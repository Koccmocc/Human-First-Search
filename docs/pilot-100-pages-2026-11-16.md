# 100-page diagnostic pilot: 2026-11-16

This Windows Release run scales the five-host diagnostic crawl from 20 to 100
admitted English pages. It checks traversal, saved artifacts and content samples
at a larger volume. It is an intermediate corpus, not the final 500–1000-page
deliverable or an extraction/language accuracy benchmark.

## Configuration and repeat command

Settings are saved in [`config/pilot-100-pages.json`](../config/pilot-100-pages.json).
Create `data/` first and choose new output names:

```powershell
./build/release/crawler/hfs-crawler.exe crawl --config config/pilot-100-pages.json --output data/pilot-100-corpus.jsonl --log data/pilot-100-log.jsonl --manifest data/pilot-100-run.json
python tools/verify_run.py data/pilot-100-run.json --check-pages
```

The allowlist retains the same five canonical hosts. Ten ordered seeds alternate
between them, with two English starting pages per host. Compared with the
20-page diagnostic config, Python's second seed is its applications page and the
RFC alias seed is replaced by the RFC series page. The deliberate German probe
is omitted. Discovery still follows all in-scope links, including directory and
service links; the seed choices are not an article-only filter.

Limits are 100 pages, 300 targets, depth 2, 1000 pending URLs, 2000 total admitted
URLs and a 300000 ms scheduling budget. The per-host interval remains 1000 ms.
Normal scope/robots checks, request timeouts, 2 MiB page body limit, redirect
checks, English admission and deduplication remain enabled.

The source checkout was `51e830c`, using application 0.1.0,
`depth-host-round-robin-v1`, `semantic-text-v3`, `lexbor-url-v1` and
`cld2-compact-v1`. The existing MinGW GCC 15.2.0 Release executable was used;
this increment changes diagnostic configuration and documentation only.

## Verification and content review

The reusable `verify_run.py --check-pages` passed for all 100 records, checking
file sizes/hashes, JSONL/accounting, per-page IDs/text hashes, uniqueness, scope,
request-chain endings, versions, status, depth and language-policy metadata.
An additional local audit matched every corpus row with its delivered journal
event, including initial/final URL, depth, response status and language result,
and checked UTC fetch times against the run. The source files were read-only.

Fifteen distinct text samples were reviewed at their start, middle and end:
the first and last delivered page per host, plus the five shortest body-fallback
pages. Observations:

- SQLite's body-fallback samples retain the repeated site menu/search prelude.
  The About page's `heading` branch starts at its page heading, as before.
- PostgreSQL's documentation directory retains its release banner and quick
  links; the event archive yields a long list of event descriptions.
- RFC content includes in-page controls, reference sections and author/contact
  metadata inside the selected main region.
- The sample includes useful explanatory prose alongside directories, archives
  and release/download lists. Language admission alone does not classify their
  usefulness for a search corpus.

Twenty-one records used `body` (18 SQLite, 3 PostgreSQL). These source labels are
review signals, not an error count; semantic/heading selection also does not prove
article quality. One record was shorter than 500 characters: PostgreSQL's policies
index, at 475. This is a diagnostic length observation, not a rejection rule.

Before scaling to the final corpus, admission-limit observability and content
selection/review need further work. The 100-record sample does not close team
integration or the final reproducibility/quality requirements.
